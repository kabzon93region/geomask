# Решение G05: отдельные hev-инстансы, фиксированные listeners, egress

**Статус:** OPEN-OWNER. Пункт плана (G05: «общий hev pid не отдельный instance/fixed
listener/egress») требует архитектурного решения владельца: это меняет топологию runtime на
роутере, а не исправляет дефект кода. Ниже — что есть сейчас, варианты, рекомендация и
критерии приёмки, чтобы решение можно было принять без чтения кода.

## Что есть сейчас (по исходникам)

- Один сервис `hev-socks5-tunnel` (`/etc/hev-socks5-tunnel/*.yml`) обслуживает AI-путь; второй
  конфиг `nop2p.yml` описан в preflight/ownership (`svc.hev-nop2p`), то есть второй инстанс
  уже подразумевается манифестом, но проверяется по тому же `pidof`.
- Правила маршрутизации к таблицам 100/101/102 и marks задаются hotplug-хуком и
  `geomask-routes.sh`; консольный путь использует свой TUN (`Console`), AI — свой.
- Статус/verify смотрят на `pidof hev-socks5-tunnel` и на наличие таблицы, а не на то, какой
  именно instance обслуживает какую политику: при двух процессах `pidof` не различает их.

Отсюда риск, который зафиксировал аудит: «общий pid» не доказывает, что AI- и bypass-клиенты
идут через *разные* туннели, и что egress каждого соответствует политике.

## Варианты

### A. Два именованных инстанса с отдельными конфигами (рекомендуется)

- `hev-ai` → `ai.yml` (TUN `AI`), `hev-nop2p` → `nop2p.yml` (TUN `VPN-noP2P`), каждый со своим
  init-скриптом и pid-файлом; `pidof` заменяется на проверку конкретного pid-файла/`procd`.
- Плюсы: каждый туннель адресуем, `verify` может доказать «AI-клиент → TUN AI → таблица 101»,
  отказ одного не ломает другой; ownership manifest уже содержит оба сервиса.
- Минусы: два процесса (память), нужно обновить init-скрипты, ownership, uninstall и
  reinstall-preflight, а также guard/monitoring; на стенде проверить reboot/update.
- Статус: согласуется с текущим manifest'ом (`svc.hev-nop2p` уже объявлен) — минимальное
  расхождение между декларацией и runtime.

### B. Один инстанс, несколько socks-listener'ов и policy-routing по mark

- Плюсы: один процесс, меньше памяти; marks уже используются.
- Минусы: mihomo/hev не даёт per-listener egress без отдельного TUN; смешение политик в одном
  процессе — ровно тот риск, который аудит и назвал. Требует нестандартных правил, сложнее
  доказывать на стенде.
- Вывод: не рекомендуется как первый шаг.

### C. Оставить как есть, ограничившись честным статусом

- Добавить в `verify`/`status` явное «инстансы не разделены: egress не доказан» и не считать
  пункт закрытым. Дешёво, но не решает задачу массовой готовности.

## Рекомендация

Вариант **A**, отдельной партией после решения владельца, с приёмкой на изолированном стенде:

1. Два init-скрипта + два конфига, каждый со своим TUN и pid-файлом; `procd`/`start_service`
   без общего `pidof`.
2. Ownership: `modules/path_ai.json`/`ai_dns.json` объявляют оба сервиса и их конфиги;
   `tests/reinstall_write_set.json` и preflight-таблица получают отдельные объекты.
3. `verify` доказывает: для AI-клиента — правило → таблица 101 → `dev AI`; для bypass —
   таблица 100/102 → свой TUN; отказ одного инстанса не выглядит как здоровье другого.
4. Uninstall/reinstall снимают оба, не задевая чужое; reboot поднимает оба.
5. Стендовые критерии: pcap/mark-проверка egress каждого клиента, kill одного инстанса,
   reboot, обновление модуля.

## Что нужно от владельца

- Подтвердить вариант (A рекомендуется) и приоритет относительно остальных стендовых gates.
- Подтвердить, что второй инстанс допустим по памяти на целевом роутере (два процесса hev).
- После согласия — отдельная партия: init-скрипты, ownership, verify, тесты, стендовая приёмка.
