## 7. Короткие архитектурные контракты этапа 0

Это зафиксированные границы следующей спецификации, а не новые реализованные API.

1. **Provider / path / module:** provider — источник узлов; path — независимая политика и transport; module — возможность релиза. Одна подписка может обслуживать несколько путей, но её P2P-запрет сохраняется во всех назначениях. Стабильные IDs не выводятся из отображаемого имени/эмодзи.
2. **Профили:** миграция текущей полной установки; один обычный путь; VPN+AI; три текущих пути. Число подписок и путей проверяется отдельно. Чистый geomask root предполагает готовый сторонний стек, не чистую прошивку без mihomo/hev/MagiTrickle.
3. **Ядро:** core и paths обязательны; диагностика входит в первую поддерживаемую поставку. Выделяемые node-filter/device-modes/ai-dns/youtube/torrent/share/update соответствуют карте основного плана. Отключение UI не снимает обязательную защиту, удаление зависимости активного пути не приводит к DIRECT.
4. **AI-допуск:** AND всех обязательных сервисных доказательств; FAIL/UNKNOWN/expiry одного результата исключает узел целиком. Обязательный путь без допуска закрыт. Нельзя заменить доказательство Google ответом ChatGPT.
5. **P2P:** явный proxy-ingress → подходящая P2P-разрешённая подписка; вне него P2P/UNKNOWN/неразрешённое BLOCKED до source rules/fixed listeners, включая ai/bypass. Не обещать универсальное распознавание замаскированного протокола; проверять допустимые классы и отрицательные случаи.
6. **Транзакция:** один владелец/lock/ревизия на общий ресурс; долгий scan не держит lock во время сети, а сверяет исходную revision перед commit. Уникальные кандидаты, журнал фаз, проверка реального runtime, сохранение первичной ошибки. Набор rulesets/config не объявляется атомарным только из-за нескольких os.replace.
7. **Backup gate:** свежий полный sysupgrade на ПК + совпадение суммы + проверенная карта покрытия/дополнения до любого изменяющего entry point. Отсутствие PC-offload не позволяет писать. Существующие автоматические writers исключения не получают.
8. **Потеря связи:** rollback-процесс/механизм запускается и проверяется **до** live apply, не зависит от SSH/браузера/агента и имеет доступ к точному прежнему состоянию без ПК. Аварийный runtime fail-closed — заранее установленная политика, не разрешение новой административной записи без бэкапа.
9. **Бюджет восстановления:** предлагаемый ориентир для спецификации — старт автоматического rollback не позже 5 секунд после обнаруженного провала, затем подтверждение фактического восстановления. Число 5 секунд — инженерное предложение, а не уже согласованный SLA и не обещание вернуть все TCP-сеансы за 5 секунд. Конкретный бюджет фиксируется и проверяется до live apply; если испытание не показывает приемлемое окно/надёжность, production apply запрещён.
10. **Проверка до apply:** кандидат `mihomo -f ... -t`, trial со всеми иными ports/paths/runtime-ресурсами; не менять live selection ради проверки. После — собственный health + соседние пути + клиентские проверки. Ни нулевой exit парсера, ни API 200 по одному endpoint не заменяют эту проверку.
11. **Management/control-plane:** до строгой политики фиксируются реальные зависимости текущего канала управления и узкие разрешения. Нельзя внедрять default-deny и обнаруживать потерю SSH/чат-провайдера постфактум. Это не широкое разрешение всего трафика роутера.
12. **Область этапа 1:** сначала локальная спецификация и тесты. Новые runtime API/типы/сигналы ещё не добавлены; code-map текущей реализации не переписывается будущей архитектурой.

## 8. Уточнённый порядок этапа 1 ради сохранения связи

Порядок основного плана сохраняется; внутри этапа 1 работы разделяются по риску:
- **1A, локально:** сохранить/перенести необходимые router-only fixes в исходники с regression-тестами, привести build parity; P12 — merge ключей, включая 0/1/custom/unknown, без живого обновления.
- **1B, локально/изолированно:** общий writer/backup/rollback-контракт, тесты гонок/обрывов/API failures и всех затрагиваемых writers. Не ставить новый writer рядом со старыми, игнорирующими его lock.
- **1C, только после доказательств:** минимальная согласованная живая группа изменений с новым свежим бэкапом и проверенным независимым rollback. Если отдельные файлы несовместимы при поштучной замене, применять подготовленный согласованный набор; не выполнять слепой `--reinstall`.
- Device/network/firewall-reconcile не смешивать с первым UI/config исправлением. Сначала доказать отсутствие source-rule fallback и испытать откат отдельно. `/etc/config/network` без отдельного согласования не менять.

Нельзя одновременно исправлять все 77 карточек или молча включать новую географию/default-deny при переносе формата. Сроки следующего этапа уточняются после его исполнимой спецификации.
