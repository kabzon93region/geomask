# Торренты и P2P: как они маршрутизируются в geomask

Задача владельца (30.10): **ни одно торрент-соединение не должно идти через mihomo-подписки**
(ни VPN, ни AI). Разница с прошлой политикой принципиальная — раньше порты трекеров
принудительно отправлялись в VPN.

## Почему нельзя «по типу трафика»

Классификатора «это BitTorrent» в стеке нет:

| Слой | Что умеет матчить | Чего не видит |
|---|---|---|
| mihomo | домен, IP, порт, процесс (только локальный трафик роутера), GEOIP/SNI | сам протокол BT |
| magitrickle | домены из DNS-ответов (ipset) + подсети | пиры, пришедшие из DHT/PEX без DNS |
| zapret | протоколы/TLS/SNI | — |

DHT, PEX и пиры — это голые TCP/UDP на случайные адреса без сигнатуры, поэтому «системно по
типу соединения» реализуется только **по source IP** (отдельное устройство/адрес) или
**по порту/списку** (то, что сделано здесь).

## Три механизма, которые действуют сейчас

### 1. Слушатель `torrent-direct` (главный)

```yaml
  - name: torrent-direct
    type: mixed          # SOCKS5 + HTTP
    port: 7894
    listen: 192.168.0.1
    proxy: AI            # фиксированная цель — AI-подписка
```

В qBittorrent: Настройки → Соединение → Прокси-сервер → SOCKS5, `192.168.0.1:7894`,
включить «Использовать прокси для работы BitTorrent» и «…для соединения с пирами»,
«Выполнять поиск имени хоста через прокси» оставить (DNS резолвится на роутере).

Проверено, что libtorrent гоняет через слушатель не только TCP, но и **UDP (DHT/µTP)** —
в conntrack видно поток `sport=41552 dport=7894` по UDP.

**Почему цель — AI, а не DIRECT (v1.16.0).** Обычная VPN-подписка запрещает P2P: 31.10 провайдер
увидел BitTorrent в своём туннеле и **заблокировал подписку** (группа `VPN` показывает
`now: 🚫 Subscription disabled`, вместо узлов — служебные записи). У AI-подписки такого запрета
нет, поэтому торренты отправлены на неё. Побочный, но важный эффект: AI-домены, попавшие в этот
слушатель, оказываются в AI — утечка AI в DIRECT исключена по построению. Эволюция:
`proxy: DIRECT` (1.14.4) → без политики, решают правила (1.15.1, чтобы AI не утекал) →
`proxy: AI` (1.16.0, закрывает и то, и другое). Вернуть DIRECT смысл есть только если ваша
VPN-подписка разрешает P2P.

Замер на живом роутере через `192.168.0.1:7894` после переключения:

```
[TCP] ... --> openrouter.ai:443   using AI[🇺 USA 6 VLESS TCP]   → HTTP 200
[TCP] ... --> 1337.abcvg.info:80  using AI[🇺 USA 6 VLESS TCP]   → HTTP 200
```

Поле `proxy:` у слушателя **не проверяется** `mihomo -t` (валидация пропускает даже заведомо
мусорное значение), поэтому всё, что касается слушателей, проверяется только рантаймом.

### 2. Страховка для трафика мимо прокси: `SRC-PORT,41552,AI`

Слушатель помогает только тому клиенту, который его указывает. Реальный слив произошёл именно
потому, что в qBittorrent прокси был **не настроен**: весь трафик шёл через TUN, где
`RULE-SET,mtrickle,VPN` с 1300 правилами `IP-CIDR` (Ovh 622, Cloudfront 243, Digitalocean 180,
Meta 117, Hetzner 84) ловит пиров на хостинговых адресах — пир `188.165.77.110` попадает в
`188.165.0.0/16` и уезжает в VPN-подписку.

```
- RULE-SET,torrentdirect,DIRECT   # трекеры — напрямую
- SRC-PORT,41552,AI               # ответы входящим пирам — в AI, не в VPN
- RULE-SET,mtrickle,VPN
```

Это накрывает соединения, инициированные **извне** (порт прослушивания как source port).
Исходящие дial'ы к пирам с эфемерных портов по-прежнему требуют включённого прокси — полная
гарантия только на стороне настроек торрент-клиента.

### 3. Ruleset `torrentdirect` — списки трекеров

`/etc/mihomo/ruleset/torrentdirect.yaml`, 108 записей: 103 домена + 5 трекеров, у которых в
объявлении стоит голый IP. Собирается из публичных списков
[ngosang/trackerslist](https://github.com/ngosang/trackerslist) (`trackers_all.txt`) и
[XIU2/TrackersListCollection](https://github.com/XIU2/TrackersListCollection) (`all.txt`);
поддомены, покрытые родителем, сворачиваются.

Правило стоит **после** `RULE-SET,ai,AI` и **до** `RULE-SET,mtrickle,VPN`:

```
- RULE-SET,ytvpn,VPN
- RULE-SET,ytdirect,DIRECT
- RULE-SET,ai,AI                # политика Google/AI всегда выигрывает
- RULE-SET,torrentdirect,DIRECT # трекеры не могут быть засосаны VPN-списками
- RULE-SET,mtrickle,VPN         # 2769 правил, из них 1300 IP-CIDR хостинга
```

Это важно, потому что `mtrickle` содержит 1300 `IP-CIDR` правил (Ovh 622, Cloudfront 243,
Digitalocean 180, Meta 117, Hetzner 84) — именно туда попадали трекеры и seedbox-пиры.

## Почему убрали фиксацию по портам (v1.15.0)

Раньше (до v1.14.4 — в VPN, затем — в DIRECT) существовал блок:

```
- DST-PORT,6969,...  - DST-PORT,1337,...  - DST-PORT,2710,...  - DST-PORT,8081,...
- DST-PORT,451,...   - DST-PORT,5944,...
```

Он стоял **в самом начале списка правил — выше `RULE-SET,ai,AI`**. Замер на роутере показал, к чему
это ведёт: `45.155.204.190:1337` (comss-релей AI) попадал под портовое правило, а не под политику AI.
После удаления правил тот же поток корректно маршрутизируется в USA:

```
45.155.204.190:1337  match RuleSet(ai) using AI[🇺 USA 6 VLESS TCP]
211.75.205.187:6969  match Match using GLOBAL[DIRECT]
```

Плюс правило по порту действовало на **любой** трафик этого порта, а не только на торрентный.
Поэтому закреплён только адресно-доменный механизм (ruleset) и прокси-слушатель.
`--check` теперь считает наличие такого правила легаси-ошибкой (`bad`).

## Управление из панели (v1.15.0)

Вкладка «Списки и синк» → карточка «Торренты и трекеры»: состояние слушателя и его адрес,
число доменов/IP в ruleset и сколько их реально загрузилось в mihomo, кнопки
«Включить/Выключить слушатель» и «Обновить списки трекеров», поле «свои домены».

Под капотом — `/usr/bin/geomask-torrent.sh`:

| Команда | Что делает |
|---|---|
| `--status` | JSON для панели (слушатель, счётчики, свои домены, источники) |
| `--refresh` | тянет публичные списки, подмешивает свои домены, сворачивает поддомены, пишет ruleset, `mihomo -t`, reload |
| `--listener on\|off` | добавляет/убирает блок `torrent-direct` в `listeners` (с валидацией и откатом) |
| `--extra "a.org b.org"` | заменяет список своих доменов и пересобирает |

Источники лежат в `/etc/geomask/torrent/sources.conf`, свои домены — в `/etc/geomask/torrent/extra.txt`
(оба сохраняются между обновлениями). Любая запись в конфиг проходит `mihomo -t` и откатывается при
ошибке; перезагрузка — через локальный API с bearer-токеном.

## Что по-прежнему не закрыто

- **Входящие пиры** (те, кто стучится на порт 41552) не проходят через прокси: они приходят на
  адрес клиента, и ответы уходят обычным путём. Их защищает механизм 2/3 (порт и списки), но
  произвольный IP пира списком не накрывается — он и не нужен: не совпав ни с одним правилом,
  он уходит в `MATCH,GLOBAL` = DIRECT.
- Если нужна 100% гарантия «вообще не касаться mihomo» — только отдельное устройство в режиме
  `bypass` (правило `ip rule priority 19900 from <ip> lookup main`, обходит перехват TUN на 32760).
  Вариант «второй IP на рабочем ПК» отклонён: `netsh add address` на DHCP-интерфейсе переводит
  адаптер в статический режим, а в qBittorrent 5.x нет привязки к интерфейсу.
- Слушатель открыт всей `br-lan` — любое устройство сможет получить DIRECT через `192.168.0.1:7894`.
  Закрывается ограничением по source IP (нужен статический адрес клиента).

## Диагностика

```sh
logread | grep -E 'tracker|RuleSet\(torrentdirect\)|using DIRECT' | tail -20
curl -s -H "Authorization: Bearer $(sed -n 's/^secret:[[:space:]]*//p' /etc/mihomo/config.yaml)" \
     http://127.0.0.1:9090/providers/rules | grep torrentdirect   # ruleCount=108
grep -nE 'DST-PORT|torrentdirect' /etc/mihomo/config.yaml
```
