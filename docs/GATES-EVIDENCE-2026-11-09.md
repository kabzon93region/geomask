# Доказательства по техническим gate плана node-audit

Дата: 09.11.2026. Здесь только то, что проверено запуском, с точной командой и наблюдаемым
результатом. Непроверенное перечислено в конце отдельно.

## Gate 1. Immutable file provider на используемой версии mihomo — ПРОЙДЕН

Проверка выполнялась на самом роутере, в изолированном процессе, живого mihomo не касаясь.
Скрипт: `scripts/checks/prove_file_provider.py`, диагностика: `scripts/checks/diag_file_provider.py`.

Наблюдения:

1. Провайдер с `type: file` и путём вне домашнего каталога mihomo **отвергается на разборе
   конфигурации**:

   ```
   parse proxy provider pool-test error: path is not subpath of home directory or
   SAFE_PATHS: /tmp/gm-provider-proof/pool.yaml
   allowed paths: [/root/.config/mihomo]
   ```

   То есть управляемые пулы обязаны лежать внутри `/root/.config/mihomo/` (или SAFE_PATHS),
   а не в `/tmp`.

2. С путём внутри разрешённого каталога `mihomo -t` даёт `exit=0`.

3. Запущенный изолированно на loopback-порту экземпляр с тремя узлами в файле-провайдере и
   группой `use: [pool-test]` + `filter: "^(node-A|node-B)$"` отдаёт через
   `/proxies/TEST` ровно `["node-A","node-B"]`, а `/providers/proxies` показывает
   `type=File`, три узла в пуле.

   Вывод: из трех узлов пула в группу попали только два проверенных. То есть точный набор
   достижим без regex по auto-updating HTTP-источнику.

4. **Загрузка провайдера асинхронна.** Сразу после старта группа может отсутствовать или быть
   пустой; через ~1–2 с она появляется. Это прямо влияет на проверку runtime: опрос «один раз
   сразу после reload» дал бы ложный провал или, хуже, ложный успех на пустой группе.

5. Живой конфиг и pid живого mihomo не изменились (`[4] live config unchanged: True |
   live pid unchanged: True`).

Следствие, уже внесённое в код: `verify_runtime` теперь опрашивает наличие каждой объявленной
группы до дедлайна `RUNTIME_VERIFY_SECONDS`, а для групп, которые мы сузили, требует непустой
состав. Покрыто тестами `tests/test_tx_verify.py` (6 тестов).

### Применение переведено на файл-провайдер

Изначально набор фиксировался regex-списком имён. После доказательства выше применение
перестроено:

1. Проверка сохраняет **точные определения** измеренных узлов в снапшот задания
   (`/etc/geomask/node-snapshots/<path>-<job>.json`, режим 600, хранятся последние 4).
2. Применение берёт снапшот этого задания, пересчитывает отпечаток каждого определения и
   сверяет с отчётом. Несовпадение, отсутствие узла или чужой снапшот — отказ.
3. Создаётся файл-провайдер `/root/.config/mihomo/geomask-pools/<path>-g<N>.yaml` (режим 600) и
   запись `proxy-providers: audit-<path>-g<N>`, группа переключается на него; `filter` снимается.
4. Отзыв возвращает исходный `use` и `filter` из записанного манифеста и удаляет провайдера и
   файл. Старые поколения удаляются.

Проверено на роутере после установки: снапшот `vpn-b03a376c…json` содержит 34 узла, режим 600;
предпросмотр сообщает `mechanism = managed-file-provider` и `previous_use = ['sub2']`; живой
конфиг подтверждает `group use=['sub2'], filter=None`, провайдеры `slot, sub, sub2`.

То есть риск «то же имя, другое определение» закрыт на уровне механизма: в пул попадают только
те определения, которые были измерены, и они перепроверяются по отпечатку перед записью.

Осталось непроверенным: сам факт переключения группы на провайдера в живом mihomo (это уже
изменение трафика и требует решения владельца).

### Настоящий Apply на живом роутере — ВЫПОЛНЕН

Цикл прошёл целиком (`scripts/checks/accept_apply_cycle.py`), с полным бэкапом перед изменением:

| Шаг | Наблюдение |
|---|---|
| Исходное состояние | `VPN` → `use: [sub2]`, 33 узла в составе |
| Свежая проверка | 9 узлов допущено |
| Apply #1 | `ok`, `node_count=9`, провайдер `audit-vpn-g4` |
| Проверка runtime | состав **ровно** 9 предложенных узлов |

После цикла: mihomo отвечает, `VPN` держит 9 узлов без остаточных legacy-фильтров,
соседние пути не затронуты (`VPN-noP2P` 12, `AI` 2), интернет с роутера работает (200/204),
pid процесса не менялся.

### Что этот прогон нашёл (и что исправлено)

Живой запуск вскрыл четыре дефекта, которых не видели ни рецензия, ни тесты:

1. **Относительный путь в транзакции.** Ключ `'config.yaml'` разрешался от рабочего каталога
   процесса и записал кандидата в `/`, а отчёт при этом показывал успех: дайджест считался по
   настоящему файлу. Теперь транзакция требует абсолютный путь и отказывает иначе.
2. **Строка вместо байтов.** Применение передавало YAML строкой, API требовал байты — отсюда
   первый `TxError`. Покрыто тестом полного прохода применения.
3. **Каталог провайдера зависит от `-d`.** Живой mihomo запущен с `-d /etc/mihomo`, поэтому
   файл-провайдер обязан лежать внутри `/etc/mihomo`, а не `/root/.config/mihomo`. Проверено
   перебором четырёх комбинаций. Плюс `rule-providers` тоже указывают на `/etc/mihomo`, поэтому
   триал копирует внутрь себя и их.
4. **YAML 1.1 против 1.2.** Живой конфиг содержит `find-process-mode: off`. PyYAML читает `off`
   как `False` и при обратной записи выдаёт `false`, на что mihomo отвечает
   «invalid find process mode». Добавлен загрузчик с семантикой YAML 1.2.
5. **Остаточный `exclude-filter`.** После переключения на управляемый провайдер старый
   исключающий фильтр продолжал сужать пул: preview показывал 9, в работе осталось 7, и
   проверка runtime этого не замечала. Теперь применение приостанавливает `filter` и
   `exclude-filter` (с восстановлением при отзыве), а проверка runtime требует **точного**
   совпадения состава, а не просто непустоты.

Тесты: 287 unit-тестов, sandbox 342/0.

## Gate 2. Прекращение запрещённой передачи при истечении срока — ПРОЙДЕН

Найденный дефект: автоматическое истечение вызывало `revoke`, то есть **снимало** фильтр.
Снятие фильтра возвращает группу к полному пулу провайдера, включая узлы, которые проверка
признала находящимися в запрещённой стране. Это fail-open.

Исправлено: истечение только помечает пул как `expired`, сохраняет ширину (`width_preserved`)
и пишет событие; расширение остаётся явным действием человека через «Отозвать фильтр».

`apply_status` теперь различает три разных факта вместо одного булева:

- `applied` — фильтр действует и доказательства свежие;
- `filter_in_force` — фильтр действует, даже если доказательства устарели;
- `evidence_age_hours` — возраст доказательств.

Проверено тестами `tests/test_apply_guards.py`: истечение не вызывает `revoke`, помечает
статус, идемпотентно; статус показывает «фильтр действует» для просроченного пула.

Панель показывает отдельное предупреждение о просроченных доказательствах с кнопкой
«Проверить сейчас» и не выдаёт это за успех.

## Gate 3. Координация писателей общего конфига — ПРОЙДЕН для ночного сканера

Дефект: ночной сканер читал `config.yaml`, минутами опрашивал узлы, затем писал результат.
Если между чтением и записью фиксировалась транзакция, сканер молча затирал её — то есть
«единый владелец» был неправдой.

Исправлено: оба места записи сканера (`--ai-guard` и основной проход) идут через
`install_config_candidate`, который берёт тот же `flock`, что и транзакция
(`/etc/geomask/.config-tx.lock`), и сравнивает sha256 текущего файла с тем, что сканер читал.
При расхождении установка отклоняется с кодом 4 и записью в лог, кандидат удаляется.

Проверено: `tests/test_scanner_cas.py` (5 тестов) — установка при неизменном конфиге;
отказ при изменённом; отказ при удалённом; приём и байтов, и текста; структурная проверка,
что обходного `os.replace(CFG+...)` не осталось.

На роутере после установки: `geomask-node-scan.sh --list-providers` → `slot,sub,sub2`,
то есть встроенная программа по-прежнему разбирается и работает.

### Дополнение: сканер не пишет в применённую группу

Найдено живым разбором конфигурации роутера: `sub_provider=all`, поэтому после применения в
перечислении провайдеров появился `audit-vpn-g6`, а группа `VPN` входит в `name_filter_groups`.
Прежняя логика `apply_filter_all` выбирала группы по провайдеру, то есть ночной прогон дописал
бы `exclude-filter` в только что применённую и проверенную группу — «единый владелец» был бы
нарушен на первом же запуске по расписанию.

Исправлено двумя штрихами:

- перечисление провайдеров исключает ids с префиксом `audit-`;
- `apply_filter_all` отказывается писать в группу управляемого провайдера (`matched=0`).

Проверено: тесты `tests/test_scanner_ownership.py` (4), на роутере перечисление отдаёт
`slot,sub,sub2` при наличии `audit-vpn-g6` в конфиге.

## Gate 4. Панель: отрисовка без браузера — ПРОЙДЕН как проверка кода

`scripts/checks/render_panel.js` загружает настоящий `assets/geo-sync-page.js` в Node с
минимальными шимами LuCI (`E`, `rpc.declare`, `view.extend`, `ui`, `document`) и вызывает
`render()` на реальных ответах четырнадцати RPC, снятых с роутера
(`scripts/checks/capture_panel_data.py`).

Результат: 641 узел дерева; присутствуют все три карточки путей, кнопки «Проверить»,
«Предпросмотр», «Применить фильтр», «Отозвать фильтр», блок расписания с кнопкой сохранения и
история. Объявлен 51 RPC-метод.

Прогон нашёл два реальных дефекта интерфейса:

1. **Не было положительного индикатора применения.** Карточка показывала предупреждение только
   при проблеме, поэтому «ничего не применено» и «применено и здорово» выглядели одинаково.
   Добавлена строка состояния: действует (с числом узлов, временем и провайдером), просрочено,
   отозвано, не применялось.
2. **Отзыв был доступен только при свежем отчёте.** А применение само делает отчёт устаревшим —
   то есть отменить его из панели было нельзя. Кнопка вынесена из условия свежести.

Что это не заменяет: нажатий в авторизованной сессии LuCI. Шимы проверяют построение дерева и
отсутствие исключений, но не реальную вёрстку, CSS и поведение контролов.

## Gate 5. Живые проверки ночного цикла и истечения — ПРОЙДЕН

`scripts/checks/live_checks.py`, выполнен на роутере с развёрнутым кодом:

```
=== scanner config write ===
unchanged install: True
refused stale base: ConfigWriteRefused
live file untouched: True
flock excludes a second writer: True

=== expiry does not widen ===
scheduler: {"ok": true, "ran": [], "expired": {"ok": true, "expired_any": true, "widened": false}}
status after expiry: expired
config digest unchanged: True
live pool size after expiry: 9
group still uses: ['audit-vpn-g6']
```

То есть: сканер действительно берёт flock, отказывает при изменённом файле и не трогает живой
конфиг; истечение помечает пул, не расширяя его, и не меняет байты конфига.

## Gate 6. Приёмка в настоящей LuCI — ПРОЙДЕНА владельцем 09.11.2026

Проверка выполнялась владельцем в браузере на живом роутере, не агентом. Найдены и исправлены
дефекты, которых не видел ни один автоматический тест:

| Что нашли | Причина | Исправление |
|---|---|---|
| `ReferenceError: pollJob is not defined` | свободная функция вместо метода view | вызов через `view.pollJob`, job ID хранится на кнопке |
| `Invalid Date` во всей истории | события не содержали поля `timestamp` | поле пишется; старые события нормализуются из `event_id` при чтении |
| ручные проверки помечены `cron` | `actor` выводился из владения блокировкой | явный параметр `actor`, планировщик передаёт `cron` |
| кнопка отмены не работала | не была добавлена в карточку; backend не останавливал worker | worker проверяет запрос отмены между узлами; кнопка в карточке |
| поток «Наблюдение прервано» | таймеры накапливались после перерисовок | один таймер на путь, вне экземпляра view; три сбоя до предупреждения |
| нет итога проверки | `reload()` молча заменял карточку | уведомление «Проверка завершена: N допущено…» |
| английские предупреждения | тексты бэкенда не переводились | переведены |
| `callNodesAuditStart` не существует | опечатка в ветке просроченного пула | существующий `callNodesPathCheck` |

Итог приёмки: история читается, проверка запускается и завершается с итогом, предпросмотр
работает, ошибок в консоли нет. Владелец подтвердил результат на своих данных.

## Gate 7. Запись о применении до транзакции — ПРОЙДЕН

Раньше запись `applied` сохранялась только после commit: падение между ними оставляло группу,
возможно уже привязанную к управляемому провайдеру, без записи об этом. Теперь запись
`status: applying` пишется **до** транзакции, при отказе восстанавливается прежняя, а
`apply_status` для `applying` сообщает `filter_in_force: true` с предупреждением — то есть
никогда не выдаёт незавершённое применение за свободный путь.

Проверено: `tests/test_apply_safety.py` (10).

## Gate 8. Идентичность узла и имена файлов снимков — ПРОЙДЕН

- Отпечаток узла покрывает **всё определение**, а не часть transport-ключей: подмена
  `uuid`/пароля при том же имени, сервере и порте больше не сохраняет одобренный отпечаток.
- `job_id` валидируется перед использованием в имени файла снимка (обход каталога отклонён).
- Предпросмотр проверяет снимок так же, как применение: если снимок не совпадает с отчётом,
  предпросмотр честно отказывает, а не обещает пул, который применение потом отвергнет.

Проверено: `tests/test_apply_safety.py`, живой отказ после смены алгоритма.

## Gate 9. Повторное применение не ломает отзыв — ПРОЙДЕН

Применение поверх уже применённого пути записывало в `previous_use` **управляемый** провайдер,
а его файл тут же удалялся при очистке поколений. Отзыв после этого вёл группу на файл, которого
больше нет. Теперь исходная подписка переносится из первой записи, старый провайдер и его файл
удаляются, а отзыв всегда возвращает настоящий источник.

Проверено: `tests/test_reapply_chain.py` (6).

## Gate 10. Границы ресурсов и честность транзакции — ПРОЙДЕН

- Снимки узлов имеют общий бюджет 8 МиБ (`GM_AUDIT_SNAPSHOT_BUDGET`). Исчерпание **отказывает**
  новую операцию, а не удаляет старый снимок, который может быть нужен предпросмотру или
  применению.
- `start_transaction` принимает ровно один файл. Раньше API обещал атомарность нескольких
  файлов, хотя писал их по одному; теперь это явный отказ с объяснением, а не мнимое обещание.

Проверено: `tests/test_resource_bounds.py` (5), на роутере — отказ при двух файлах.

## Gate 11. Восстановление после прерванной транзакции — ПРОЙДЕН

Функция восстановления существовала, имела тесты и **не вызывалась ниоткуда**: транзакция,
прерванная посреди commit, оставалась прерванной до тех пор, пока это не заметит человек.
Теперь `start_transaction` восстанавливает предыдущую прерванную транзакцию до того, как
положить новое изменение поверх неё, и отказывается продолжать, если восстановление невозможно.

Журнал на роутере: 54 записи, восстановление на чистом состоянии ничего не меняет, конфиг
побайтно тот же. Проверено: `tests/test_recovery_wiring.py` (6) — восстановление вызывается
до записи, отказ при неудаче, откат прерванного commit, неприкосновенность завершённого,
отказ применять повреждённый предобраз.

## Gate 12. Незавершённый ввод не теряется — ПРОЙДЕН

План требовал, чтобы сохранение в одной карточке не стирало ввод в другой. Перезагрузка
страницы (в том числе автоматическая после проверки) очищала поля всех карточек. Теперь
несохранённый ввод каждой карточки хранится отдельно, восстанавливается при перерисовке,
помечается строкой «есть несохранённый ввод» и сбрасывается после успешного сохранения.

Проверено: `scripts/checks/test_panel_actions.js` — ввод в поле, повторная отрисовка, значение
на месте.

## Gate 13. Желаемые и действующие страны различаются явно — ПРОЙДЕН

План требовал показывать разницу, когда она есть. Карточка показывала только желаемые страны,
хотя применённый пул может достигать меньшего набора. Теперь запись применения хранит
фактически измеренные страны пула (`acting_countries`), GET отдаёт их, а карточка при
расхождении пишет: «Желаемые страны: DE,FR,NL,PL · действующие: DE,NL».

Проверено: `tests/test_acting_countries.py` (5) и тест панели на отрисовку обеих строк.

## Gate 14. Подписку, на которую опирается путь, нельзя удалить — ПРОЙДЕН

Реестр подписок удалялся по номеру без проверки: если путь всё ещё читает эту подписку,
группа оставалась с провайдером, чей источник исчез. Теперь удаление сначала спрашивает
mihomo-конфиг, какие группы используют провайдера с этим URL, и отказывает, пока путь не
переключён.

Проверено на роутере: `source-in-use` для реальной подписки отвечает `in_use: true,
providers: [sub2]`, для выдуманного адреса — `false`. Тесты: `tests/test_source_delete_guard.py` (7).

### Отдельно: дефект в собственном скрипте развёртывания

Первый заход этой правки сломал RPC: файлы записывались с правами 644, и `geo-backend.sh`
потерял бит исполнения — rpcd не смог его запустить, все вызовы отвечали «No response».
Скрипт откатился, но и откат ставил 644, поэтому поломка сохранялась. Права восстановлены,
а установка теперь сохраняет режим существующего файла и проверяет исполнимость бэкенда
перед объявлением успеха.

## Gate 15. AI-допуск по ChatGPT и Cloudflare — ПРОЙДЕН по решению владельца

**Решение владельца 09.11.2026:** принимать AI-узел по ChatGPT и Cloudflare, Google помечать
как «неизмеримый» и не требовать.

Основание — живая проба: Google отдаёт страницу выдачи, но не раскрывает страну ни в одном
машинно-читаемом виде. Требовать Google означало блокировать каждый узел навсегда, ничего не
доказывая о его выходе.

Что изменено:

- `AI_REQUIRED_SERVICES = ['cloudflare', 'chatgpt']`, `AI_INFORMATIONAL_SERVICES = ['google']`.
  Google по-прежнему опрашивается и записывается, но не участвует в вердикте.
- В отчёте у каждого AI-узла есть блок `informational.google` с `measured`, `country` и
  `policy: not-required`; в причинах отказа Google больше не появляется.
- Подпись отчёта и карточка панели объясняют критерий прямым текстом.

Живая проверка AI-пути после развёртывания:

```
status  : complete | counts: {'eligible': 4, 'excluded': 32, 'unknown': 0}
🇺🇸 USA        cf=US  chatgpt=US  google=unmeasurable
🇺🇸 USA-HY2    cf=US  chatgpt=US  google=unmeasurable
🇺🇸 USA 2      cf=US  chatgpt=US  google=unmeasurable
🇺🇸 USA 2-HY2  cf=US  chatgpt=US  google=unmeasurable
```

Исключённые узлы отклонены по измеренной стране ChatGPT и Cloudflare (NL, DE и т. д.), а не по
неизвестности. Предпросмотр предлагает ровно эти 4 узла и предупреждает, что унаследованные
`filter` и `exclude-filter` будут приостановлены на время действия пула.

Проверено тестами: `tests/test_node_audit.py` — допуск по паре, отказ при чужой стране ChatGPT,
`unknown` при неизмеримом ChatGPT, измеренная страна Google не гейтит, у VPN-путей блока
`informational` нет.

## Gate 16. Готовность к последнему шагу — применение из админки владельцем

План требует, чтобы владелец **сам** в админке применил результат и после обновления увидел
именно этот рабочий пул. Всё, что нужно до нажатия, проверено:

| Проверка | Результат |
|---|---|
| Свежий отчёт VPN | `24f5f8980d732df722275a04`, `complete`, не устарел |
| Предпросмотр VPN | `ok`, 10 допущено, 13 исключено, 11 неизвестно |
| Предлагаемый пул | 8 × DE, 2 × NL — ровно измеренные узлы |
| `preview_id` | выдан, применение примет его |
| Текущее состояние | `revoked`: фильтр не действует, путь на исходном `sub2` |
| Отчёт AI | 4 допущено (US), предпросмотр готов |

Осталось одно действие, которое может сделать только владелец: нажать «Применить фильтр» в
панели. Кнопка вызывает тот же RPC, которым уже прогонялся полный цикл apply → verify → revoke.

## Gate 17. Отчёт несёт методику, очистка не трогает нужное — ПРОЙДЕН

План требовал, чтобы отчёт содержал версию и контекст методики, а очистка не удаляла материал,
на который ссылаются активные записи.

- Каждый отчёт теперь содержит `probe_version` и `probe_context` (DNS-контекст, список
  сервисов, критерий допуска). Живая проверка AI: `service-egress-2`,
  `{"admission": "chatgpt+cloudflare", "dns": "remote SOCKS5h", "services": ["cloudflare",
  "chatgpt", "google"]}`.
- Удержание снимков принимает список защищённых job id: снимок, на который ссылается
  применённая запись или предыдущий отчёт, не удаляется при ротации.

Проверено: `tests/test_report_method_retention.py` (7) — версия объявлена, наборы сервисов не
пересекаются, Google не входит в допуск, защищённый снимок переживает ротацию, незащищённый
удаляется, запись с защитой не ломается.

## Gate 18. Незавершённое применение не выглядит как «не применялось» — ПРОЙДЕН

Состояние `applying` (применение в полёте или оборванное между commit и записью) попадало в
ветку «по умолчанию», и карточка писала «Фильтр не применялся» — хотя группа могла быть уже
привязана к управляемому провайдеру. Теперь у этого состояния своя строка-предупреждение:
«Применение не завершено: пул может быть уже подключён. Проверьте состав и при необходимости
отзовите фильтр».

Проверено: тест панели, где все пути находятся в `applying`, — надписи «не применялся» нет.

## Gate 19. Готовый проверщик состояния применения

`scripts/checks/verify_apply_state.py` сверяет после нажатия: фактический состав группы против
записи применения, отсутствие активных legacy-фильтров у применённого пути, неприкосновенность
соседних путей и неизменность pid mihomo. Прогон на текущем состоянии (ничего не применено)
корректен: `vpn revoked`, остальные `never`, живые группы на `sub2` / `sub` / `slot`.

Отдельно зафиксировано: у `AI` сейчас активны `filter` и `exclude-filter`, у `VPN-noP2P` —
`exclude-filter`. При применении они будут приостановлены и восстановлены при отзыве; проверщик
это контролирует.

## Gate 20. Кнопки «Применить» и «Отозвать» проверены нажатием — ПРОЙДЕН

Именно такой класс ошибки ломал `pollJob`: обработчик ссылался на несуществующее имя, и кнопка
падала, хотя отрисовка выглядела нормально. Поэтому кнопки применения проверены кликом в
изолированном стенде, с проверкой **точных аргументов** вызовов:

| Нажатие | Что уходит в RPC |
|---|---|
| «Предпросмотр» | `nodes_path_preview('vpn', 'job-1', 'rev-1', 'src-1')` |
| «Применить фильтр» после предпросмотра | `nodes_path_apply('vpn', 'preview-123', 'rev-1')` |
| «Применить фильтр» без предпросмотра | вызова нет, отказ «Сначала сделайте предпросмотр» |
| «Отозвать фильтр» при действующем фильтре | вызов есть, итог сообщается |
| «Отозвать фильтр» без фильтра | кнопки нет вовсе |

Это не заменяет живое нажатие владельцем, но доказывает, что кнопки связаны с правильными
методами и передают правильные аргументы.

## Gate 21. Планировщик после всех правок сигнатур — ПРОЙДЕН

Живой тик на роутере: `rc=0`, 0.9 с, `{"ok": true, "ran": [], "expired": {"ok": true,
"expired_any": false, "widened": false}}`. Cron-запись на месте (`crontab` содержит
`geomask-audit-schedule`), отдельного init-скрипта нет — расписание живёт в cron, как и задумано.
Тик ничего не запускал, потому что до 03:30 далеко; проверено именно то, что модуль не сломался
после появления параметра `actor` и защищённых снимков.

### Важное состояние расписания на 17:05

| Путь | Расписание | Режим |
|---|---|---|
| VPN | включено, 03:30 | **проверка и применение** (изменено 15:22:17) |
| VPN-noP2P | выключено | только проверка |
| AI | выключено | только проверка |

Режим VPN «проверка и применение» означает, что в 03:30 планировщик сам выполнит проверку и,
если найдутся допущенные узлы, **применит** их без участия владельца. Это записанное решение
владельца (событие `schedule-set`, 15:22:17), а не действие агента; менять его без указания
нельзя.

## Gate 22. Ночной путь применения проверен целиком — ПРОЙДЕН, найден дефект

Прежние тесты планировщика подменяли `preview_apply` и `apply_preview` заглушками, поэтому
настоящая цепочка «проверка → предпросмотр → применение» в ночном режиме не исполнялась ни разу.
Новый тест `tests/test_scheduler_apply_chain.py` прогоняет реальные функции на настоящем отчёте,
снимке и конфиге.

Тест сразу нашёл дефект: `_compile_eligible_pool` собирал допущенные узлы только из имени,
провайдера и отпечатка — **измерения узла терялись**. Из-за этого `acting_countries` всегда
получался пустым, то есть строка «действующие страны» в панели никогда бы не появилась, хотя
модульный тест самой функции проходил. Теперь измерения едут вместе с узлом.

Проверено: ночной прогон применяет пул через настоящий предпросмотр (`applied`, `node_count`,
`previous_use` = исходная подписка, `acting_countries` непусты); устаревшая ревизия источника
останавливает ночное применение; пустой пул не применяется.

## Gate 23. Состояния «просрочено» и «подтверждено» показаны честно — ПРОЙДЕН

Панель проверена на граничных состояниях, а не только на «применено»:

- `expired` → «доказательства просрочены», и путь **не** выдаётся за «не применялся»;
- здоровое `applied` с `runtime_verified: true` → «Фильтр действует», без ложного предупреждения
  о расхождении с работающим mihomo;
- `applying` → отдельное предупреждение, не «не применялся».

Журнал планировщика: cron-запись `*/5 * * * * … >>/var/log/geomask-audit-schedule.log 2>&1`,
файл существует (17 КБ), последние строки — корректный JSON. То есть ночной прогон оставит след,
даже если ничего не запускалось.

## Gate 24. Журнал транзакций ограничен, восстановление не врёт — ПРОЙДЕН

Два связанных дефекта в аварийном пути:

1. Журнал транзакций рос без границы (на роутере 54 записи, 10 КБ, и дальше только вверх).
   Теперь он ограничен 400 записями и 256 КиБ, но **незавершённые транзакции не удаляются** —
   иначе восстановление потеряло бы свои предобразы.
2. `_restore_preimages` возвращал «успех», если записей предобразов вообще не нашлось: то есть
   восстановление отчитывалось о завершении, ничего не восстановив. Теперь отсутствие предобразов
   даёт `recovery_failed`, а не тихий успех.

Проверено: `tests/test_tx_journal_retention.py` (5) и на роутере — обрезка журнала ничего не
удалила при 54 записях, `_restore_preimages` для неизвестной транзакции возвращает `False`.

## Gate 25. Устаревший отчёт объясняется, а не тупикует — ПРОЙДЕН

Живой случай от владельца: проверка VPN завершилась в 19:34:04, **после** того как страница
загрузила прежний отчёт. Кнопка «Предпросмотр» отправила старый `job_id` и получила
`Report ID mismatch; run a fresh check` — технически верно, но тупик без объяснения.

Теперь панель распознаёт эту группу ошибок (устаревший/отсутствующий/незавершённый отчёт),
перечитывает данные и пишет: «Отчёт обновился после загрузки страницы. Данные перечитаны —
нажмите «Предпросмотр» ещё раз». Сырой текст бэкенда владельцу не показывается.

Проверено тестом панели: подставной ответ `Report ID mismatch` даёт понятное сообщение и
перечитывание, а не голую ошибку.

## Что осталось непроверенным

1. **Google-география — проверено и остаётся открытым.** Через реальный узел получена выдача
   Google (HTTP 200, 93 КБ) без согласия и CAPTCHA; в теле нет ни `uule`, ни `region`/
   `countryCode`/`country`/`gl`, ни `data-country`, ни «Google offered in». Программного
   признака страны нет. Детали: [RESEARCH-GOOGLE-GEO](RESEARCH-GOOGLE-GEO-2026-11-08.md).
   Это блокирует полный AI admission, но не VPN и не VPN-noP2P.
2. **Браузерная приёмка LuCI — выполнена владельцем** (Gate 6). Остались только нажатия
   Apply/Revoke из панели: живой цикл проверялся через тот же RPC, но кнопками применялся
   лишь отзыв.
3. **Полный ночной цикл в реальном времени.** Проверено на роутере: сканер берёт настоящий
   flock, отказывает при изменённом файле и не трогает живой конфиг; отдельно проверено, что
   истечение срока помечает пул, не расширяя его (`widened: false`, состав 9 узлов, дайджест
   конфига не изменился). Совместный ночной прогон с одновременной транзакцией в реальном
   времени не воспроизводился.
4. **Реестр владения** не спрашивается сканером: координация сделана через общий lock и CAS,
   а не через реестр `owner`.
5. **24-часовое ожидание.** Истечение проверено подменой отметки времени, а не выжиданием суток.
